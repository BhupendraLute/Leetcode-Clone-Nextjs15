## 1. CRITICAL - Will Crash or Break Build

### 1.1 `next build --turbopack` Fails

**File:** `package.json` (line: scripts.build)

```json
"build": "next build --turbopack"
```

**Problem:** The `--turbopack` flag is **only** supported in `next dev`. In `next build`, it is silently ignored at best or causes unexpected behavior at worst. Turbopack is still experimental for production builds.

**Fix:**
```json
"build": "next build"
```

---

### 1.2 `currentUserRole` Crashes When User Not in DB

**File:** `modules/auth/actions/index.js:72`

```js
const userRole = await db.user.findUnique({
  where: { clerkId: id },
  select: { role: true }
});
return userRole.role;  // CRASHES if userRole is null
```

**Problem:** If a user exists in Clerk but hasn't been onboarded yet (no DB row), `findUnique` returns `null`. Accessing `.role` on `null` throws: `Cannot read properties of null (reading 'role')`. The catch block returns `{ success: false, error: "Failed to fetch user role" }` — a **completely different shape** than the string the root layout expects.

**This crashes the entire root layout** whenever a signed-in user visits who isn't in the DB yet.

**Root layout uses it:** `app/(root)/layout.js:6`
```js
const userRole = await currentUserRole();  // could crash or return { success: false, error }
// ...
<Navbar userRole={userRole} />  // receives broken shape
```

**Fix:**
```js
export const currentUserRole = async () => {
  try {
    const user = await currentUser();
    if (!user) return null;
    const userRole = await db.user.findUnique({
      where: { clerkId: user.id },
      select: { role: true }
    });
    return userRole?.role ?? null;
  } catch (error) {
    console.error("Error fetching user role:", error);
    return null;
  }
};
```

**Then in Navbar:** handle `null`/`undefined` gracefully.

---

### 1.3 `connectionString` Becomes `"undefined"` When ENV Missing

**File:** `lib/db.js:5`

```js
const connectionString = `${process.env.DATABASE_URL}`;
```

**Problem:** If `DATABASE_URL` is undefined, template literal converts it to the **string `"undefined"`**, not `undefined`. `PrismaPg` will try to connect to a database called `undefined` with a confusing error message instead of a clear "missing env var" error.

**Fix:**
```js
const connectionString = process.env.DATABASE_URL;
if (!connectionString) throw new Error("DATABASE_URL environment variable is required");
```

---

### 1.4 Prisma Adapter Created Unnecessarily on Every Import

**File:** `lib/db.js:5-7`

```js
const connectionString = `${process.env.DATABASE_URL}`;
const adapter = new PrismaPg({ connectionString });
const prisma = new PrismaClient({ adapter });
```

**Problem:** `new PrismaPg(...)` and `new PrismaClient(...)` run at module evaluation time on every import, even when `globalForPrisma.prisma` already exists. In production, it runs every time anyway (no global caching in serverless).

**Fix:** Lazily initialize or restructure to only create when needed:
```js
const globalForPrisma = globalThis;
export const db = globalForPrisma.prisma ?? createPrismaClient();
if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = db;
```

Where `createPrismaClient()` is a function.

### 2.2 No Rate Limiting on Server Actions

**File:** `modules/auth/actions/index.js`

**Problem:** `onBoardUser` can be called repeatedly with no rate limiting. A malicious actor could spam this endpoint.

**Fix:** Use something like `express-rate-limit` pattern or implement rate limiting at the middleware level or use a library like `upstash-rate-limit` if using Redis. At minimum, debounce on the client side.

---

### 2.3 No Input Validation on Server Actions

**File:** `modules/auth/actions/index.js`

**Problem:** While these specific actions derive data from Clerk (trusted), as the app grows, all server actions need input validation. Clerk's `currentUser()` is trusted, but future actions taking form data need Zod or similar validation.

**Fix:** Adopt Zod for all server action input validation going forward.

---

### 2.4 Middleware Matcher Regex Complexity

**File:** `middleware.js:9-13`

```js
matcher: [
  '/((?!_next|[^?]*\\.(?:html?|css|js(?!on)|jpe?g|webp|png|gif|svg|ttf|woff2?|ico|csv|docx?|xlsx?|zip|webmanifest)).*)',
  '/(api|trpc)(.*)',
],
```

**Problem:** The complex regex can miss edge cases (e.g., `.map` files, `.json` files with query params). Also, the `(api|trpc)` pattern matches routes that don't exist in this project.

**Fix:** Simplify or stick with the default Clerk middleware matcher.

## 3. DATA INTEGRITY & EDGE CASES

### 3.1 Empty Email Allowed Despite `@unique` Constraint

**File:** `modules/auth/actions/index.js:24`

```js
email: emailAddresses[0]?.emailAddress || "",
```

**Problem:** If a Clerk user has no email addresses (edge case), the email becomes `""`. The DB has `email String @unique` — the **first** user without an email succeeds, but the **second** one throws a unique constraint violation with a confusing error because `""` is not unique.

**Fix:** Handle this case explicitly:
```js
const email = emailAddresses[0]?.emailAddress;
if (!email) return { success: false, error: "User must have an email address" };
```

---

### 3.2 Home Page Calls `onBoardUser` on Every Render

**File:** `app/(root)/page.js:25`

```js
export default async function Home() {
  await onBoardUser();
```

**Problem:** Every single visit to `/` — including by unauthenticated users — calls `currentUser()` (Clerk API call) and potentially a DB upsert. For unauthenticated users, this does nothing but still makes the Clerk lookup. For authenticated users, it runs an unnecessary DB call on every page load.

**Fix:** `onBoardUser` should only run once — either via webhooks (recommended) or by checking if the user exists first. For unauthenticated users, bail out immediately before the Clerk call.

---

### 3.3 Home Page Uses Hardcoded Fake Stats

**File:** `app/(root)/page.js:54-59`

```js
const stats = [
  { number: "50K+", label: "Problems Solved" },
  { number: "10K+", label: "Active Developers" },
  // ...
];
```

**Problem:** Hardcoded with no actual backend data. These will never be accurate without a background job or real-time aggregation.

**Fix:** Either: (a) Compute from real database queries, or (b) Remove until the app has real data.

### 3.4 Navbar Links to Non-Existent Routes

**File:** `modules/home/components/navbar.jsx:31-48`

Routes `/problems`, `/about`, `/profile` are linked but **none of them exist** — they will all return 404.

## 4. ARCHITECTURE & DESIGN

### 4.1 No TypeScript in Source Files

**Problem:** The project uses `jsconfig.json` but all source files are `.js`/`.jsx`. Prisma generates full TypeScript types, and Clerk provides typed SDKs, but none of this type safety is used. This leads to runtime errors like Issue 1.2.

**Fix:** Migrate to TypeScript (`.ts`/`.tsx`). Start by renaming critical files and adding types.

---

### 4.2 No Error Boundaries or Fallback Routes

**Missing files:** `error.js`, `loading.js`, `not-found.js`, `global-error.js`

**Problem:** If any server component throws, the entire app shows a white screen or Next.js generic error. Users get no meaningful error feedback.

**Fix:** Create these files at the root level:
- `app/error.js` — catches errors in server components
- `app/loading.js` — Suspense fallback during navigation
- `app/not-found.js` — Custom 404 page

---

### 4.3 Server/Client Boundary Inefficiency

**File:** `app/(root)/layout.js` → `modules/home/components/navbar.jsx`

**Problem:** `userRole` is fetched in a server component and passed as prop to a client component. This means:
- Any role update requires a full server component re-render (page refresh)
- The Navbar can't reactively update the role

**Fix:** Use a combination approach: pass initial role from server, but also fetch/refresh from client using Clerk's `useUser()` hook to get real-time auth state.

---

### 4.4 All Auth Logic in a Single File

**File:** `modules/auth/actions/index.js`

**Problem:** As the auth module grows, putting all server actions in one file becomes unwieldy.

**Fix:** Split into separate files per domain: `onboard.js`, `roles.js`, etc.

---

### 4.5 `problems/[id]/page.jsx` Is a Placeholder

**File:** `app/problems/[id]/page.jsx`

```jsx
const ProblemPage = () => {
  return <div>ProblemPage</div>;
};
```

**Problem:** This page doesn't even access the dynamic `params.id`. In Next.js 15, params is a Promise that must be awaited.

**Fix:**
```jsx
const ProblemPage = async ({ params }) => {
  const { id } = await params;
  return <div>Problem: {id}</div>;
};
```

## 8. DATABASE & PRISMA

### 8.1 Only One Database Model Exists

**File:** `prisma/schema.prisma`

The entire schema has only `User`. A LeetCode clone needs at minimum:
- `Problem` — title, description, difficulty, test cases, etc.
- `Submission` — user, problem, code, language, status, result
- `TestCase` — input, expected output, problem relation
- `Category` / `Tag` — for organizing problems

---

### 8.2 Missing Database Indexes

**File:** `prisma/schema.prisma`

Only `@unique` indexes exist on `clerkId` and `email`. No indexes on foreign keys or frequently queried fields.

**Fix:** Add indexes on fields used in `where` clauses, especially as the schema grows.

---

### 8.3 PostgreSQL on Non-Standard Port 5433

**File:** `docker-compose.yml`

```yaml
ports:
  - "5433:5432"
```

**Problem:** This is non-standard and can cause confusion. If another Postgres instance runs on 5432, this conflicts differently.

**Fix:** Document this clearly and ensure the `.env.example` uses port 5433.

---

### 8.4 No Health Check in Docker Compose

**File:** `docker-compose.yml`

**Problem:** The `next dev` command in `package.json` does `docker compose up -d && next dev`. If Postgres isn't ready when Prisma tries to connect, the app crashes.

**Fix:**
```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres"]
  interval: 5s
  timeout: 5s
  retries: 5
```

---

### 8.5 `prisma.config.ts` May Not Compile

**File:** `prisma.config.ts`

**Problem:** This TypeScript file imports `dotenv/config` and uses `defineConfig`. Without ts-node or a build step, `prisma` CLI may not be able to process this file correctly depending on the environment.

**Fix:** Ensure `prisma` is run with the correct Node.js and TypeScript setup, or keep it as plain JS.

## 10. INFRASTRUCTURE & DEVOPS

### 10.1 No Node Version Specified

**Missing:** `.nvmrc` or `engines` field in `package.json`.

**Fix:**
```json
"engines": { "node": ">=18.17.0" }
```

---

### 10.2 Docker Compose in Dev Script is Opinionated

**File:** `package.json`

```json
"dev": "docker compose up -d && next dev --turbopack"
```

**Problem:** Forces Docker usage. A developer using a local Postgres instance or a cloud DB can't simply run `npm run dev`.

**Fix:** Separate scripts:
```json
"dev": "next dev --turbopack",
"dev:db": "docker compose up -d",
"dev:all": "docker compose up -d && next dev --turbopack"
```

---

### 10.3 `.gitignore` Has Semicolons on Comment Lines

**File:** `.gitignore` - Lines like `.yarn/*; !.yarn/patches; !.yarn/plugins;` have semicolons which are likely copy-paste artifacts from a Unix `.gitignore` that used `;` as comment. Semicolons are **not comment characters** in gitignore — they're treated as literal characters in file names.

**Fix:** Remove trailing semicolons from pattern lines.
